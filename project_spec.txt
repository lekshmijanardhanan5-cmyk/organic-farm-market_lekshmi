Organic farm market System 

1. PROJECT OVERVIEW
-------------------
Project Title:Organic farm market
Tech Stack: MERN (MongoDB, Express, React, Node.js)

2. PROBLEM STATEMENT
--------------------
“Lack of a transparent, direct-to-consumer platform for organic farmers results in reduced farmer income, higher consumer prices, and food wastage.”

3. PROPOSED SOLUTION
--------------------
A digital platform that directly connects verified local organic farmers with consumers, enabling transparent pricing, reduced wastage, and assured product authenticity.

4. USER ROLES & PERMISSIONS
---------------------------
This simplified academic model contains three user roles: Admin, Farmer, and Customer. Roles are mutually exclusive and determine which parts of the system a user can access and which actions they may perform.

- **Admin**
  - Can approve or reject farmer registrations (manage farmer approval state).
  - Can view, create, update, and delete any product.
  - Can view and manage all orders in the system.
  - Can block or delete user accounts.
  - Purpose: overall system administration and trust/quality control.

- **Farmer**
  - Can create and update their own profile.
  - Can create, update, and delete products they own.
  - Can view and manage orders that contain their products (accept, pack, mark as delivered).
  - Cannot manage other farmers' products or orders.
  - Purpose: list and sell produce and manage order fulfillment for their products.

- **Customer**
  - Can browse and view products and product details.
  - Can place orders for available products.
  - Can view their own order history and order statuses.
  - Purpose: purchase products from farmers.

5. DATABASE STRUCTURE (Schemas)
-------------------------------

  The simplified database for the academic model contains four schemas: User, Product, Order, and Transaction. Each schema focuses only on the fields required for core functionality.

   A. User Schema
Name (String, Required)
Email (String, Unique, Required)
Password (String, Hashed, Required)
PhoneNumber (String, Optional)
Address (String, Optional)
Place (String, Optional)
Landmark (String, Optional)
Pincode (String, Optional - 6 digits)
FarmName (String, Optional - for farmers)
ProductTypes (Array of Strings, Optional - for farmers)
YearsOfExperience (Number, Optional - for farmers)
Role (String: 'admin' | 'farmer' | 'customer', Default: 'customer')
IsApproved (Boolean, Default: true for admin/customer, false for farmers)
IsBlocked (Boolean, Default: false)
CreatedAt (Timestamp)
UpdatedAt (Timestamp)

   B. Product Schema
Title (String, Required)
Description (String, Optional)
Price (Number, Required)
Category (String, Optional)
ImageUrl (String, Optional)
Farmer (Reference to User, Required)
IsAvailable (Boolean, Default: true)
CreatedAt (Timestamp)
UpdatedAt (Timestamp)

   C. Order Schema
  User (Reference to User – Customer, Required)
  Items (Array of Objects: { Product (Reference to Product), Quantity (Number, min: 1) }, Required)
  TotalAmount (Number, Required)
  Status (String: 'Pending' | 'Accepted' | 'Packed' | 'Delivered', Default: 'Pending')
  PaymentMethod (String: 'COD' | 'UPI' | 'CARD', Default: 'COD', Required)
  UpiId (String, Required if PaymentMethod is 'UPI')
  CardLast4 (String, Optional; stored when PaymentMethod is 'CARD')
  PaymentStatus (String: 'Pending' | 'Paid' | 'Failed', Default: 'Pending')
  CreatedAt (Timestamp)
  UpdatedAt (Timestamp)

  D. Transaction Schema (Payment/Sales Ledger)
  Order (Reference to Order, Optional; created only on successful payment)
  Customer (Reference to User – Customer, Required)
  Farmers (Array of References to User – involved farmers, Required)
  Items (Array of Objects: { Product (ref), Farmer (ref), Title (String), Quantity (Number), UnitPrice (Number) }, Required)
  TotalAmount (Number, Required)
  PaymentMethod (String: 'COD' | 'UPI' | 'CARD', Required)
  PaymentStatus (String: 'Pending' | 'Paid' | 'Failed', Required)
  TransactionStatus (String: 'Initiated' | 'Completed' | 'Failed', Default: 'Initiated')
  GatewaySessionId (String, Optional)
  GatewayTransactionId (String, Optional)
  UpiId (String, Optional; stored when PaymentMethod is 'UPI')
  CardLast4 (String, Optional; stored when PaymentMethod is 'CARD')
  Meta (Object, Optional; gateway-specific metadata)
  CreatedAt (Timestamp)
  UpdatedAt (Timestamp)


6. FEATURE WORKFLOW (The "User Journey")
----------------------------------------
1. Login
User logs in and lands on the Product Page.

2. Browse
User sees a grid/list of Organic Products (fetched from database).
User can click on any product to view detailed product information.

3. Product Details
User views full product details including description, price, and farmer info.

4. Order & Payment
User clicks "Order Now" on a selected product and enters quantity.
User selects a payment method (Cash on Delivery, UPI, or Card).

- If `COD` is selected: the simulated checkout confirms immediately and creates the order with `paymentStatus = 'Pending'` (payment is considered pending until delivery), and creates a corresponding `Transaction` with `transactionStatus = 'Completed'`.
- If `UPI` is selected: the frontend first initiates a simulated payment gateway session via `/api/orders/checkout/initiate`, then confirms the payment via `/api/orders/checkout/confirm` (demo flow). On success, the backend creates both `Transaction` and `Order` with `paymentStatus = 'Paid'` and stores `upiId`.
- If `CARD` is selected: the frontend similarly goes through `/api/orders/checkout/initiate` then `/api/orders/checkout/confirm`. On success, the backend creates both `Transaction` and `Order` with `paymentStatus = 'Paid'` and stores `cardLast4`.

If the simulated UPI/CARD confirmation fails, the backend does not create the `Order`, but still records a `Transaction` with `paymentStatus = 'Failed'` and `transactionStatus = 'Failed'`.

5. Farmer/Admin View
Farmer/Admin refreshes dashboard and sees the new order.
Farmer can accept/pack orders containing their products.

6. Order Fulfillment & Notifications
After an order is placed:
- The order appears in the farmer's dashboard (farmers see only orders containing their products).
- The farmer can accept and pack orders that include their products and mark them as delivered when complete.
- Admins can also view and update order statuses across the system.
- Users see order status updates in their order history (Pending → Accepted → Packed → Delivered).
- Payment method (COD/UPI/CARD) and relevant payment identifiers (UPI ID and/or card last4, if applicable) are displayed in admin and farmer order views.

Real-time Updates
- The system supports Server-Sent Events (SSE) for real-time order status updates.
- Customers, farmers, and admins can subscribe to order status changes via the SSE endpoint.
- Order status changes are broadcasted in real-time to authorized subscribers.

User Notification
Users see the order status updated (Pending → Accepted → Packed → Delivered) within their order history, along with payment method and payment status information.
7. API ENDPOINTS (The URL Rules)
--------------------------------
Authentication
POST /api/auth/register → Register new user (validates role: admin, farmer, customer)
POST /api/auth/login → Login user (blocks login if account is blocked)
GET /api/auth/profile → Get logged-in user profile (returns all user fields except password)
PUT /api/auth/profile → Update user profile (validates email, phone number, pincode formats)

Customer
GET /api/customer/stats → Get customer statistics (orders by status, total spent)

Farmer
GET /api/farmer/products → Get farmer's own products
DELETE /api/farmer/products/:id → Delete farmer's own product (only if owner)
GET /api/farmer/stats → Get farmer statistics (total products, orders by status, revenue from delivered orders)

Products
GET /api/products → Get list of organic products (public - only from approved and non-blocked farmers)
GET /api/products/:id → Get single product by ID (public - only if farmer is approved and not blocked)
POST /api/products → Create new product (Farmer/Admin - farmers must be approved and not blocked)
PUT /api/products/:id → Update product (Farmer/Admin - farmers can only update their own products)
DELETE /api/products/:id → Delete product (Admin or product owner farmer)

Orders
POST /api/orders → Legacy single-call order placement (requires: `items` and `paymentMethod`; `upiId` required if `paymentMethod` is `UPI`; `CARD` is supported as a simplified/legacy flow)
POST /api/orders/checkout/initiate → Simulated gateway session init (requires: `items`, `paymentMethod`, and `paymentDetails` where `paymentDetails` is `{ upiId }` for UPI or `{ cardNumber, cardHolderName, expiryMonth, expiryYear, cvv }` for CARD)
POST /api/orders/checkout/confirm → Simulated gateway confirm + finalizes checkout (requires: `items`, `paymentMethod`, `paymentDetails`, plus `gatewaySessionId`; UPI/CARD also pass `outcome` like `'SUCCESS'`)
GET /api/orders/user → Get user orders (with optional status filter)
GET /api/orders/farmer → Get farmer orders (only products from logged-in farmer, with optional status filter)
GET /api/orders/subscribe/:orderId → Subscribe to real-time order status updates via Server-Sent Events (SSE)
PUT /api/orders/:id/status → Update order status (Farmer/Admin)

Transactions
GET /api/transactions/customer → Get transactions for the logged-in customer
GET /api/transactions/farmer → Get transactions that involve the logged-in farmer
GET /api/transactions/admin → Get all transactions (admin)

Admin
GET /api/admin/roles → Get available user roles
GET /api/admin/users → Get all users (with optional filters: role, isApproved, isBlocked)
PUT /api/admin/users/:id/approve → Approve/reject farmer
PUT /api/admin/users/:id/block → Block/unblock user
DELETE /api/admin/users/:id → Delete user
GET /api/admin/products → Get all products (includes unapproved farmer products)
GET /api/admin/orders → Get all orders (with populated user and product details)
GET /api/admin/stats → Get dashboard statistics (users, products, orders, revenue, pending farmers, blocked users)
